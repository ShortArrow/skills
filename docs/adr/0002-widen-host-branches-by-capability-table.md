# 2. ホストの追加は能力表の行として足し、最後に「Any other host」の行を置く

日付: 2026-08-28

## 状態

採用

## 背景

ADR 0001でホスト固有の手順を分岐させることを決め、分岐はClaude Codeと
Codexの2つで固定された。そこにGitHub Copilot、Cursor、Gemini CLIを足したい。

0001の形をそのまま延長すると、skill1つにつきホストごとの節が5つから6つ
並ぶ。節は見出しと導入文と手順を持つので、増えるのは手順そのものより
その周りの文である。`request-approval`のように手順が3行で済むskillでも、
本文はホストの数だけ厚くなる。

厚みを避ける道は一般化だが、それは0001が退けたものである。
「ホストの承認機構を使う」に寄せた瞬間、どのツールを呼ぶかの判断が
読み手に戻る。ホストが2つのときに危ういと判断したことは、
ホストが6つになれば動機の強さの分だけ危うい。

## 決定

ホストの追加は、能力ごとの表に行を足す形で行う。skillの節を増やさない。

行に書くのは、そのホストの公式文書に載っている機構だけとする。ツール名を
補って揃えることはしない。文書に載っていない能力は
`not documented (checked 2026-08-28); use the row below`のように、
載っていないことと確認日を書き、最終行へ送る。

表の最後には`Any other host`の行を必ず置く。この行には代替手順を具体的に
書き、あわせて禁止事項を書く。ツールをprose中で模倣しないこと、subagentが
走ったふりをしないこと、他ホストのスクリプトに落ちないことの3つである。

`tests/check-portability.ps1`の不変条件を、Claude Codeのぶんに加えて
Codexのぶんと新しいホストのぶんにも持つ。ホストごとに、そのホストの行が
消えたら真っ先に失われる文字列を1つ選んで照合する。`runSubagent`、
`ask_user`、`browser_agent`のような、他ホストの語では代用できない名前を選ぶ。

## 理由

節ではなく行にすると、ホストを足す作業が1能力につき1行の追記になる。
追記の場所が表の中に決まっているので、既存の行を読み直す理由がない。
0001が言った「分岐の追加は加算であって置換ではない」を、
ホストが増えても保つための形がこれである。

`Any other host`の行は、一般化が起きるとすればそこである。「ホストの流儀に
従う」と書けば全ホストを覆えるが、覆っただけで何も指示していない。
だから原則ではなく動作を書く。禁止事項を並べるのは、この行に来る読み手が
持っている選択肢が、たいてい他ホストの手順の流用だからである。

新しいホストにも不変条件を置くのは、Codexの記述が一度そうなりかけたため
である。あとから来る整理が、6行の表を1つの言い方にまとめる方向へ働くとき、
その差分はレビューでは短くなったように見える。文字列の照合は読まれなくても
失敗する。

## 影響

ホストを1つ足す作業は、skillごとに1行、能力ごとに1行の追記になる。
skillの数ではなく能力の数で増える。

`not documented (checked 2026-08-28)`と書いた行は、確認日が本文に残る。
文書の古さが読む側に見える代わりに、ホスト側が機能を足したときは
こちらが古いままになる。日付は更新の合図として機能する。

テストが守るのは文字列が在ることだけで、その手順がそのホストで正しく
動くことは何も保証しない。そちらは実機のセッションで確かめる必要がある。
0001の時点でClaude Codeについて言えたことが、ホストが増えても変わらない。
