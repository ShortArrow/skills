# 1. ホスト固有のskill手順は分岐させ、既存ホストの手順はテストで固定する

日付: 2026-08-23

## 状態

採用

## 背景

このリポジトリのskillはClaude Code向けに書かれ、本文が具体的なツール名と
手順を名指ししていた。`AskUserQuestion`を呼ぶ、`Read`の`pages`でPDFを開く、
`Agent`の`model`にopusを渡す、といった記述である。skillが有効に働くのは
この具体性のためで、「ホストの承認機構を使う」と一般化された指示は、
どのツールを呼べばよいかを読み手に決めさせてしまう。

Codexでも同じskillを使いたくなったが、これらのツール名はCodexには存在しない。
`SKILL.md`というファイル形式自体は複数のエージェントで共通でも、ツール名と
承認機構はランタイムのプロトコルであって、移植可能な内容ではない。

素朴な移植は、両ホストに当てはまる言い方へ書き換えることになる。それは
Codexで動くようにする過程でClaude Code側の具体性を削る、という取引になる。
削られたことは差分では目立たず、skillが少し曖昧になるだけなので、
後から気づきにくい。

## 決定

ホスト固有のskill手順は一般化して置換せず、ホスト別に分岐する。既存ホストの
具体的なツール名と手順は回帰テストで不変条件として固定する。

分岐は、まずホストを判定させ、それからホストごとの節または表を置く形をとる。
既存ホストの記述は分岐の一方としてそのまま残す。

不変条件は`tests/check-portability.ps1`が持つ。skillごとに、失われては困る
文字列を列挙して照合する。`request-approval`なら`AskUserQuestion`、
`pdf-transcribe`なら`Read(file_path="spec.pdf", pages="1-5")`のように、
一般化されると真っ先に消える箇所を選ぶ。

## 理由

一般化が起きたことをテストが検出できる。prose中の注意書きは、書き換える者が
それを読んで従うことに依存する。文字列の照合は、読まれなくても失敗する。

分岐は差分に現れるが、一般化は現れにくい。「AskUserQuestionを呼ぶ」が
「ホストの承認機構を使う」になった差分は、レビューでは改善に見える。
テストはこの区別をつけられる。

新しいホストを足す作業が、既存ホストの記述に触れる理由を持たなくなる。
分岐の追加は加算であって、置換ではない。

## 影響

skillの本文はホストの数だけ長くなる。descriptionは常時読み込まれるが本文は
発火時のみなので、この長さは常時のコストにはならない。

ホストを足すたびに不変条件の追加が要る。テストは既存ホストを守るだけで、
新しいホスト側の記述が正しいことは何も保証しない。そちらは実機で確かめる
必要がある。

`$claudeInvariants`は配列で持つ。1つのskillが複数の不変条件を持つため、
skill名をキーにした連想配列では表現できない。

Codex側の記述には出典と確認日を添える。他ホストの機能はこのリポジトリからは
検証できず、時間とともに古くなるため。
